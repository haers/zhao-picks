# Toolkits 实测：PDF 合并可用，图片切图暂不推荐

> 体验日期：2026-10-23。本文是定向评测，不是整站推荐。网站可能更新，以下结论只对应当日测试。

Toolkits 是一个提供多种小工具的开源网站。我的关注点是两件具体事情：把多个 PDF 按顺序合成一个文件，以及把创作图片裁成九宫格并打包下载。实际体验后，PDF 的正常流程可用，图片切图卡在裁剪页面 404；目前没有为这两项用途保留完整源码或维护个人 Fork 的必要，保留这份评测即可。

旧资料中可能仍称它为 YgkTool。当前评测以可核对的 Toolkits 仓库为准。所读源码版本与线上部署版本没有建立对应关系，不能把源码版本当作线上版本证明。

## PDF：正常合并可用，异常反馈不够

测试用了三个不含私人信息的合成 PDF：A 有两页，B、C 各一页。桌面和手机分别添加 A、B，将 B 移到 A 前面，再执行合并。两种视口都实际下载了 PDF，独立重读得到三页，顺序为 B-1、A-1、A-2；三页输出也分别渲染核对过。添加 C 后再删除，列表能正确移除它。

![桌面 PDF 合并，B 已移到 A 前面](../assets/toolkits/pdf-desktop.png)

手机的排序操作通过行菜单完成。390×844 视口下页面没有整体横向溢出。这些结果支持它作为普通文件的临时合并工具，但还不足以把整站作为成熟工具推荐。

实际遇到的缺口：

- 损坏 PDF 合并时抛出 `No PDF header found`，页面没有明确告诉用户哪个文件失败；合并按钮仍可点击。
- 加密 PDF 抛出加密相关错误，页面同样缺少可操作提示。测试没有尝试绕过密码保护。
- 所测文件选择入口未启用多选。固定源码及原函数探针也显示，多文件回调只消费首项；这项探针不能冒充实际拖拽测试。
- 独立浏览器测试出现过 React #418 水合错误，正常合并仍能完成。错误存在，但不能仅凭错误编号推断全部根因。

另一个源码层面的维护问题是下载资源清理：原保存函数探针连续调用三次，创建了三个 Object URL 和隐藏链接节点，没有对应回收。它是需要改进的实现细节，本轮没有测量长期浏览器内存增长。

## 九宫格：设计有用途，主流程没有跑通

这个功能吸引我的地方是“先裁成正方形，再生成九张图和 ZIP”，贴近图片发布的交付过程。但测试在入口就遇到了问题：按钮写着 `Select File`，实际文件控件却带有 `directory` 和 `webkitdirectory` 属性，要求选择文件夹，无法按正常单图选择方式导入。

为了继续观察后面的流程，我使用只含一张 900×900 合成九色块 PNG 的临时文件夹导入，没有修改页面 DOM，也没有注入修复。桌面和手机都打开了裁剪弹层，但内部内容是 404。

![手机裁剪弹层显示 404](../assets/toolkits/crop-mobile-404.png)

裁剪 iframe 请求 `/_micro/Cropper`，实际交互中被重定向到带语言前缀的页面后返回 404。“使用照片”仍能点击，但点击后弹层不关闭，没有九宫格预览，也没有下载按钮。关闭按钮可以退出，换一个测试文件后能再次打开弹层。

大小写和语言前缀的 HTTP 对照请求也都返回 404。因此，不能把修复简化成“改一下路径大小写就行”。固定源码的目录组织和语言路由还需要一起排查。

损坏 PNG 也进入同一个 404 弹层。由于没有到达图片解码阶段，本轮无法判断损坏图片的解码错误提示是否有效。九宫格生成和 ZIP 下载都没有通过，不能因为源码中存在生成函数就写成可用。

## 测试边界与使用建议

测试使用已安装 Chrome 的独立临时配置，桌面 1440×1000、手机 390×844、DPR 1。输入均为合成文件，没有使用私人文件或登录账号。截图中英文页面与中文裁剪弹层的混用是当时实际状态。临时浏览器在测试后关闭。

所读 PDF、切图链路主要在浏览器内处理文件，记录到的这些测试请求没有 POST、PUT 等写请求。这不等于整站离线，也不能承诺其他工具或未来版本不会上传文件。敏感资料应按自己的隐私要求选择工具。

我的取舍是：需要临时合并普通 PDF 时，可以参考上述局限尝试官方页面；九宫格切图当前不推荐。其他工具、GIF 和整站能力没有验收。技术栈较新、功能数量较多，都不能替代对具体用途的验证。
